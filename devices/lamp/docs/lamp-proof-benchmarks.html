What this is for

Proof, not promises.

Lamp should be judged by how present, expressive, reliable, and safe it feels in a real room — not by CPU charts or an impressive but meaningless AI score.

Use this page as the source of truth for launch claims. Product marketing gets the outcomes; engineering keeps the repeatable method, release build, environment, run count, and raw evidence behind every number.

Test method

Make every number defendable.

The benchmark should model a person using Lamp at a desk, not a perfect lab sequence that no owner will ever repeat.

Minimum record for each run

Device and software build · room noise / light · network state · chosen AI provider · input transcript · timestamps for each observable event · result · video or Flow Monitor trace. Report failures instead of deleting them.

Interaction proof

Does it feel immediate?

Capture the complete path from a real human action to an observable Lamp response.

  • Simple voice command → light or body response
  • Conversation → first spoken response
  • Emotion request → LED + body language
Presence proof

Does it feel aware?

Validate a return-to-desk moment rather than showing a generic object-detection frame.

  • Known person enters → orientation + greeting
  • Person moves → natural tracking behavior
  • Room becomes idle → dim, rest, and wake behavior
Recovery proof

Does it come back?

Real devices lose Wi‑Fi, reboot, and receive interrupted updates. Demonstrate the recovery path.

  • Network drop → reconnect and usable state
  • Service restart → camera / voice / LED healthy again
  • Interrupted OTA → safe recovery or clear rollback
Safety proof

Does it know its bounds?

Show that safety is a device property, not a polite request to an AI model.

  • Motion limits and emergency-stop behavior
  • Quiet / sleep behavior and safe wake
  • Invalid emotion or action never bypasses bounds

The demo to film

One day. One companion.

This is the product story the public should understand in seconds. It is also an end-to-end acceptance scenario for the release candidate.

1. You arrive.

Lamp notices a familiar person, turns toward them, lights up, and gives a brief greeting.

2. You settle in.

It becomes quiet and unobtrusive. The device is present without asking for attention.

3. You need something.

A short spoken command gets a fast physical response. A deeper question becomes a natural conversation.

4. Something changes.

Lamp notices a relevant moment, shows curiosity or thought through movement and light, then responds appropriately.

5. You leave.

After the room becomes idle, it dims, rests, and safely wakes when you return.

Release gates

What must be true before a claim ships.

  • Every public metric has a release build, run count, p50/p95 or success-rate definition, and retained evidence.
  • Every filmed behavior is reproducible from the same device build, not manually staged or edited into a false sequence.
  • Privacy and safety wording is checked against the current implementation and device configuration.
  • Failure and recovery paths are tested alongside the happy-path demo.
  • Marketing uses customer outcomes; the detailed method remains available for review.

Design handoff

What makes the proof visible.

Film real behavior. Use the metrics as a quiet confidence layer, never as the product’s entire personality.

  • 01 / Reel10–15 seconds: curious → thinking → happy → excited → sleepy, with the LED and body motion clearly visible.
  • 02 / PresenceOne unbroken shot: person enters → Lamp turns → greeting begins. Capture enough of the room to make the reaction believable.
  • 03 / VoiceOne short command and one real follow-up question, with natural subtitles and no hidden cuts through the response.
  • 04 / TrustMinimal visual card for local-first sensing, explicit physical bounds, quiet/sleep behavior, and safe recovery.
  • 05 / ProofA compact benchmark strip: tested build, run count, p95 / success rate, and a link to the method.
